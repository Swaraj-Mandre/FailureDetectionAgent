1The problem

A text-to-SQL agent can fail in three ways. Loud: the tool throws an error. Quiet: the SQL runs and the number is wrong. Spreading: the next turn builds on the wrong number. Our shop database (Sahyadri Stores: 40 customers, 25 products, 300 orders, April to September 2026) has no "amount" column on purpose, so revenue must be worked out, and the model can get it wrong. PBA 1 catches the loud failures. PBA 2 catches all three.

2PBA 1: one agent that notices its tool failing Units 1 and 2

diagram 01

One tool, run_sql: read-only, one SELECT at a time, and a clear Error: message on bad input (write words, several statements, unknown columns). route_after_tools checks every tool result of the turn and sends failures to handle_failure.

What the slide version did

Sent one generic message for every failure. The agent retried a dead database, sent the same broken query 7 times, and once told a user to run a DELETE by hand.

Our refinement

Classify the error, give a specific hint, cap retries at 3, detect repeated queries, and lock the tool when retrying cannot help (unsafe or unreachable). Details: ta1/REFINEMENT_NOTES.md.

Blind spot

Nothing looks at the data, so a wrong number with no error goes straight to the user. That is why PBA 2 has a Monitor.

What the Monitor checks, and why it has no model

A 3B model checking another 3B model shares its blind spots, so the Monitor uses rules worked out from the data: no negative money, nothing above all-time gross sales (Rs 12,99,209), no single order above the largest real order (Rs 16,189), no count above the largest table (757 rows), and no SUM or COUNT next to a plain column without GROUP BY. It also rejects an answer that is not backed by a valid result or misquotes the number.

What got better

  • Wrong numbers given to the user: 4 of 15 runs down to none.
  • Silent corruption: PBA 1 reported Rs 24,03,00,20 every time; PBA 2 caught it and refused to guess.
  • Unsafe and unreachable cases end after one model call, half of PBA 1's cost.

What got worse

  • 2 to 3 times the calls and time when something needs fixing (corrupt: 6.0 vs 2.0).
  • One extra call on the clean question: the team rules in the prompt make the model drop GROUP BY, and the Monitor sends it back.
  • A fault that never clears uses all 3 retries before stopping.

How it spreads: the bad number goes into the answer, the answer stays in the shared history, and the next turn builds on it. How containment works: the Monitor replaces the bad ToolMessage with a quarantine note that has the same message id, before any agent reads it.

Cost: 6.0 vs 4.0 model calls, 5.5 vs 3.5 seconds per question.

Found by our own evaluation

The first full run showed PBA 2 wrong on the clean question 3 times out of 3. The Executor had written SELECT p.name, SUM(...) with no GROUP BY. SQLite runs that without an error and returns one row: the whole month's revenue next to one arbitrary product. Our number bounds could not see it, because the total was real. The same bug gave PBA 1's wrong answer (Rs 8,13,186.80 for one order). We fixed the checks, not the judge: the Monitor now reads the SQL, Recovery names the GROUP BY to add, and the guide says never to hide bad rows with a filter. Clean question: 3/3 wrong became 3/3 correct.

10Limits

  • Small samples. 3 runs per case, 10 for containment. At temperature 0 they show stability more than spread.
  • The Monitor only knows what we wrote down. A wrong answer inside the limits, such as filtering order lines instead of order totals, still gets through.
  • The model invents stand-ins for data we do not have (loyalty points). Neither version catches it.
  • One model, one database. A bigger model makes fewer SQL mistakes, so the cost gap would shrink.

11Next steps

  • Stop early when the same check fails twice with the same numbers.
  • Let owners add their own limits next to their glossary ("an order is never above Rs 50,000").
  • Real Postgres or MySQL through a read-only user, with the same checks.
  • A page that shows the answer, the SQL behind it, and every time the Monitor stepped in.
